## 2. 调研发现：事实与设计推论

### 2.1 拍摄时间不等于入库时间

**依据：** Apple Photos 公开帮助区分按添加日期和拍摄日期排序，按添加日期时最近加入的媒体在底部。[S1]

**推论：** “最新在底部”本身不足以定义时间线。今天导入一张十年前的照片，是排到今天还是十年前，必须确定。

**推荐：** 默认按拍摄时间排列，另提供“最近添加”视图；最近添加对云端资产指服务端入库时间，不使用客户端下载时间替代。拍摄时间优先使用服务端提供的规范化资产时间；缺失时采用明确且一致的回退规则，不能让三端各算一遍而结果不同。

**仍需工程验证：** 目标服务端日期语义、时区与分页支持。跨时区照片是按拍摄地日期分组还是转换到当前设备时区分组，需要单独确认。

### 2.2 权限不是“允许 / 拒绝”两个状态

**依据：** iOS 支持有限照片库访问；Android 支持所选照片访问，并要求处理授权变化。HarmonyOS 提供 PhotoViewPicker，批量访问图库的 READ_IMAGEVIDEO 为受限权限，官方列出备份和相册整理等可申请场景；审批与用户授权是不同环节。[S2][S3][S4][S5]

**推论：** 若照片 Tab 合并本机与云端，必须设计完整、部分、拒绝、撤销授权四类状态。仅能看见部分照片不能显示为“手机没有照片”。

**推荐：** 未开启本机功能时不强求图库权限；浏览云端不依赖本机图库授权。手动上传使用系统选片；自动扫描备份在用户主动开启后，再申请所需访问权限。权限不足时保留云端浏览和手动选择上传，不阻断全 App。

**注意：** PhotoViewPicker 对已选择文件的授权不等于自动获取未来新增照片；各平台 URI 有效期与持久化方式不同，不建立“所有系统 Picker 都临时”或“都永久”的错误假设。Google Play 对广泛照片权限另有核心用途声明与审核要求。[S13]

### 2.3 系统相册不是第三方云备份的能力保证

**依据：** Apple 有 Background Tasks 等机制；Android 区分延迟任务与用户发起的数据传输；HarmonyOS 长时任务按实际业务类型管理，托管上传与应用进程持续运行不是一回事。[S6][S7][S8]

**推论：** 统一“待上传、上传中、等待 Wi-Fi、系统调度中、失败、已备份”的语义，但不能承诺锁屏、退出或系统终止后三端都即时扫描并上传。任务完成通知与暂停原因应准确反映实测能力。

**推荐：** 默认备份由用户开启，首次确认范围、原件策略和网络条件；提供手动继续、暂停和失败重试；不显示无法保证的精确剩余时间。选择自动备份作为首发能力前，先完成鸿蒙权限与三平台后台可行性验证。

### 2.4 “删除本机”可能影响其他云服务

**依据：** Apple 明确指出，开启 iCloud Photos 时，从设备图库删除会同步影响同账户其他设备；Google Photos 对主删除与 Delete from device 有不同语义。[S9][S10]

**推论：** 不能照搬系统相册的一个垃圾桶按钮，隐式同时删 Immich 和系统图库。“释放空间”也不是简单清理应用缓存。

**推荐：** 默认云端操作只作用于 Immich；本机图库删除作为分开的显式操作。清理缓存不能调用系统图库删除。即使用户选择删除本机，也必须提示系统云同步可能扩散影响，不能保证“只影响这台手机”。

**服务端限制：** Immich 回收站可以被管理员关闭，保留时间可配置，客户端不能写死可恢复天数或永远承诺可恢复。[S11]

### 2.5 相册权限、列表排序和相册内部排序是不同概念

**依据：** Immich 公开文档区分共享相册 viewer / editor；相册 API 的 order 为相册内部资产排序，不等于整个相册列表的拼音排序或置顶。[S12][S14]

**推论：** 能看见不等于可以修改；需要分别定义相册列表、置顶组、相册内照片顺序和共享标识。

**推荐：** 普通相册列表遵循已确认的拼音 / 字母顺序；置顶组单独位于顶部。初版组内也按名称排序。置顶按“服务端地址 + 用户 + 相册 ID”隔离保存；是否跨设备同步待验证目标服务端的用户偏好能力。本轮查到的相册 DTO 不足以证明服务器支持或完全不支持置顶同步。

### 2.6 搜索能力由服务端版本、配置、索引和模型共同决定

**依据：** Immich 公开文档区分元数据过滤与 CLIP 语义搜索，说明不同模型的语言支持不同；搜索还可涉及人物、地点、OCR 等。[S15]

**推论：** “服务器有搜索接口”不等于中文语义搜索始终可用；关闭机器学习、索引未完成、未授权、网络故障与真正零结果不是同一状态。

**推荐：** 日期、媒体类型等确定性过滤作为基础；智能搜索按能力展示并注明作用范围。文字检索、语义检索和人物入口不混为一个无解释的黑盒。不能根据本机未上传照片的缩略图，暗示服务端已经能搜索它们。

### 2.7 连续多选与原比例瀑布流存在体验取舍

**依据：** 用户已确定连续范围选择和纵向保留滚动；Apple 无障碍指南建议为手势提供可见替代入口，优先熟悉操作。[S16]

**设计判断，不是平台强制规则：** 原比例错列瀑布流更突出构图，但连续范围、跨行斜向选择与缩放重排更难预测。等大方格更利于选区理解和稳定定位。

**推荐：** 照片 Tab 优先等大方格，默认三列、二至六列为手机端初始原型候选；完整构图在大图呈现。最终列数随窗口宽度和可访问性适配。这只是候选，不将相册已确认的二至四列上限套给照片流。

### 2.8 分享不是只弹出分享面板

**依据：** Apple 提醒带有位置元数据的照片可能让接收者获知拍摄地点；Immich 公开文档支持带有效期、密码等配置的公开链接。[S17][S12]

**推论：** 分享文件 / 分享链接、预览 / 原件、静态照片 / 实况、是否保留位置，都涉及隐私或媒体完整性决策。

**推荐：** 普通分享优先实际文件与系统分享面板；提供清晰的原件和兼容副本选项。对兼容分享副本建议默认移除 GPS，明确告知可能改变元数据；原件导出不悄悄改写原件。公开链接作为独立操作，不能把原件中转到第三方服务或静默创建公开访问。

## 5. 可沿用默认规范，无需用户逐项选技术参数

以下是质量底线或可逆的低风险默认值，不应每项都变成问卷：

- 跟随系统深浅色、字号与减少动态效果，媒体查看器可采用稳定的深色背景候选。
- 交互目标满足平台可访问性要求，图标带语义标签，状态不只依赖颜色。
- 手势保留可见入口；键盘、系统返回、安全区域和系统分享正确适配。
- 空内容、无搜索结果、未授权、部分授权、断网、服务器错误、缩略图失败、存储不足分别说明。
- 异步操作显示真实结果，处理取消、重试和部分成功；操作后避免无故跳动。
- 首次说明精简，权限在使用时申请，不连续弹出无关权限。
- 数据与凭据按账户隔离，日志脱敏，不把令牌写进普通 UI 或公开日志。
- 不引入第三方媒体分析或公开链接中转，除非用户另行批准相应产品方案与隐私披露。
- 缩放 / 方向判定 / 弹簧参数、组件 API 与 FFI 类型由工程验证，不要求用户拍脑袋定毫秒和角度。

品牌色、App 名称、图标、留白、顶栏样式等属于视觉稿确认阶段；不应早于 A 类产品边界和照片流原型。跨平台保持语义一致，不要求像素级一致。

## 6. 建议确认顺序

1. 第一轮（已完成）：A1 资产来源、A2 首发范围、A3 资料库职责、A4 时间排序。结果见第 3 节。
2. 第二轮（核心方向已记录，边界待确认）：A5 删除语义、A6 账户范围、A7 搜索结构、A8 共享范围，详见专项规范。
3. 第三轮：照片网格已定正方形默认五列 / 二至十五列、备份先选相册再开启、回收站后本机内容继续显示并右下角标记；日期定位、多选回拖和跨屏规则继续结合原型确认。已确认收藏先存本 App、系统按能力联动、正常上传并匹配后同步当前账户 Immich 收藏；完整同步方向后定。曾同步后手动删除云端的本机照片用专用右下角图标区分，只有明确手动上传才能重传，加云端相册不触发上传。证据与边界见 [收藏能力调研](FAVORITES_SYNC_FEASIBILITY.md)。

每轮最多四个主问题，先给推荐与取舍；具体决策结果另行回写交互规范，未回答的项保持待确认，不自动视为同意。

## 7. 验证任务：比截图相似更重要

- 今天上传十年前的照片：能解释它去了哪里，并能在最近添加中找到。
- 云端照片正常可看，本机权限只授权三张：不能显示手机空库或要求重登。
- 长按 2 拖到 7，再回拖到 4：选区变化可预测；竖向滑动不误选。
- 浏览数年前照片时同步新照片、缩放列数、打开大图再返回：原位置保持稳定。
- 本机与云端都有同一张照片：不重复计数；删除确认明确影响范围。
- 回收站已关闭 / 用户只有只读权限 / 批量操作部分失败：正确阻止或解释，不假装成功。
- 实况只上传静态图成功：不能标记完整备份；播放资源缺失可降级。
- 退出登录后切换另一账户：不泄漏前账户缩略图、置顶、搜索历史或后台上传目的地。
- 离线查看与清缓存：用户能区分缓存可看、离线原件和远端备份。
- 大字体、读屏、减少动态效果下仍能完成选择、返回和删除确认。
