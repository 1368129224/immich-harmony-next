# 跨平台相册 UI 与交互策略（建议稿）

> 范围：HarmonyOS NEXT、iOS、Android。本文是产品设计建议，不表示已有跨平台实现，也不是对各系统最新版相册的逐项实测报告。具体平台 API、组件与手势应在目标系统版本上验证。
>
> 已确认的产品要求及待定交互细节见 [App 信息架构与交互规范](APP_INTERACTION_SPEC.md)。具体产品决策以该规范中的已确认条目为准。

## 1. 推荐结论

采用 **统一产品语言 + 平台原生交互**，而不是三端像素级一致，也不是分别复刻三个系统相册。

用户应该认得这是同一个 App，但不需要为了使用它重新学习手机的基本操作。

- 统一“产品是什么”：功能语义、内容组织、媒体状态、品牌、数据规则。
- 原生化“如何操作”：返回、导航呈现、菜单、分享、权限、触觉反馈与无障碍。
- 在照片主舞台保留自己的设计：时间线、网格、查看器、备份状态和多选反馈。

## 2. 三种路线对比

| 维度 | 三端完全统一 | 各自复刻系统相册 | 统一产品 + 原生适配 |
| --- | --- | --- | --- |
| 品牌辨识与跨端迁移 | 强 | 弱，产品结构容易分裂 | 强，核心概念一致 |
| 单平台学习成本 | 自定义交互可能增加负担 | 熟悉，但未必适合云相册 | 基本操作熟悉，业务规则明确 |
| 开发维护 | 规范统一；原生三套 UI 仍需维护 | 易演变为三套产品路线 | 共用业务契约，维护平台呈现差异 |
| OS 演进 | 自定义组件仍需适配 | 容易被系统相册改版牵着走 | 跟进规范，不追逐每次外观变化 |
| 云端 / 本地语义 | 可以统一 | 系统相册模型未必适用 | 产品自主定义并跨端一致 |

相册以内容为中心，品牌不必依赖醒目的装饰；清晰的媒体状态、流畅的浏览和可靠的数据操作，比所有按钮长得完全一样更重要。

## 3. 必须统一的部分

### 产品结构与命名

- 三端保持同一组一级产品目的地与命名：底部从左到右为**照片、相册、搜索、资料库**。资料库采用照片分类 + 管理入口，搜索结构仍待定义，不因平台随意增加或隐藏核心功能。
- 导航目的地一致，不等于控件形状、位置和转场必须一致。
- 搜索、相册、收藏等操作的结果语义一致，入口可做平台适配。

### 时间线与媒体语义

- 日期分组、排序、时区处理和搜索过滤规则一致。
- 明确区分云端资产、本机照片、已备份、待备份、失败和仅有缓存等状态；状态不可只靠颜色区分。
- 照片、视频和实况媒体的能力与降级行为清晰；平台不支持某种播放或导出时，不伪装成功。
- 收藏、归档、相册归属等业务语义一致，避免跨端使用时产生歧义。

### 高风险操作

- “云端移入回收站”“删除本机原件”“清理应用缓存 / 账户本地数据”必须区分，确认文案说明实际影响；服务器回收站不可用时不能静默变成永久删除。
- 已确认多服务器多账户与登录历史，操作和后台任务按目标账户隔离；共享按目标 Web 普通用户功能核对，不能把共享可见性当成删除权限。
- 不将某个平台系统相册的删除行为直接套用于 Immich 服务端。
- 回收站、撤销或恢复能力仅在实际具备对应服务端 / 平台能力时呈现。

### 品牌与设计令牌

- 统一品牌色角色、内容留白原则、圆角层级、媒体状态图例和文案语气。
- 字体优先跟随系统，支持动态字号、高对比度与减少动态效果。
- 统一语义令牌，而非所有平台共享完全相同的字号、触摸目标与动画常数。

## 4. 应适配平台的部分

| 场景 | iOS | Android | HarmonyOS NEXT |
| --- | --- | --- | --- |
| 返回与页面层级 | 遵循系统导航栈及适用的侧滑返回 | 正确接入系统返回；按目标版本适配预测性返回 | 遵循 ArkUI 路由和系统返回机制 |
| 导航与菜单 | 按平台规范选择标签栏、工具栏、上下文菜单 | 按 Material 规范选择导航栏、顶栏、菜单 | 按 HarmonyOS 规范选择导航、工具栏与菜单 |
| 权限、分享与媒体选择 | 使用系统提供的流程与授权模型 | 使用系统提供的流程与授权模型 | 使用系统提供的流程与授权模型 |
| 媒体保存、导出与实况播放 | 使用 iOS 能力并验证格式支持 | 使用 Android 能力并验证格式支持 | 使用 HarmonyOS 能力并验证格式支持 |
| 后台备份 | 尊重系统调度，不承诺持续后台运行 | 尊重系统及厂商后台限制 | 尊重系统任务生命周期与权限限制 |
| 触觉、动画与无障碍 | 遵循系统习惯和用户偏好 | 遵循系统习惯和用户偏好 | 遵循系统习惯和用户偏好 |

Android 没有唯一的“原生相册”：Google Photos 与不同厂商相册的产品定位和交互不完全一致。应以 Android / Material 平台规范为基线，参考目标用户的设备习惯，而不是把某一家相册当成全平台标准。

iOS Photos 和 HarmonyOS 相册同样只是参考对象，不是必须完整复刻的产品规格。

## 5. 关键相册交互的建议

### 时间线

三端均采用本机与云端合并的照片流，同一已匹配资产不重复展示，支持全部 / 云端 / 本机筛选。默认按拍摄时间排列，另设最近添加；最新照片位于底部，默认进入时定位到底部，支持双指缩放调整列数与密度。已确认正方形缩略图默认四列，缩放二至十五列；同步状态暂定右下角图标，云端入回收站但本机仍在时继续展示并用特定图标区分。横屏布局随窗口与无障碍设置适配。不要求同尺寸截图像素级一致。

### 多选

统一“进入选择模式 → 明确选择状态 → 批量操作”的状态模型。已确定长按进入多选，水平 / 斜向滑动按起终点连续范围选择，纵向滑动保留为照片流滚动。建议各端补充清晰的显式入口，不要用隐藏手势代替唯一入口。方向识别与手势锁定需原型验证。

### 查看器

统一浏览目标：左右切换、缩放、播放、查看信息、分享和返回。每次打开大图默认显示工具栏，含收藏、加相册、删除类操作、分享。仅本机提供本机删除；双端存在时提供本机删除及云端回收站两个操作并禁止自动重传（除非手动）；仅云端时删除改为回收站。具体布局与提示边界见 [专项规范](DELETION_ACCOUNT_SHARING_SPEC.md)。单击照片切换工具栏显隐，左右切图保持当前显隐状态。

具体手势遵循平台预期，并处理冲突：图片已放大时先平移图片；图片处于适合退出的状态时再响应关闭手势；不要抢占系统边缘返回。滑动关闭、实况播放触发方式等必须在真机验证，不能只凭静态设计决定。

### 备份与离线

已确认首发包含自动备份，先选择本机相册再开启；只备份当前浏览账户，切换时暂停旧账户并按新账户自身配置运行。统一“待备份 / 上传中 / 已完成 / 失败 / 等待条件”等状态语义，但准确呈现不同平台的执行条件，并验证授权、队列、重试、后台调度和实况完整性。区分“缓存可查看”和“原件已备份”，不以相同 UI 暗示相同后台能力。

## 6. 与当前架构的关系

- `crates/immich-core`：继续承载可复用的 HTTP、API 兼容、数据库、缓存等逻辑；已确认 Immich 多版本接口、Schema、能力探测与回退在 Rust 中间层适配，向 UI 提供统一语义与能力状态，不要求用户先选定固定服务器版本。业务规则按职责逐步集中，而不是复制到三个 UI 中。
- 系统图库收藏读取 / 写入及授权属于平台能力，Rust 负责本地意图与云端同步契约，不能用服务端多版本适配绕过 OS 限制；降级候选见 [收藏能力调研](FAVORITES_SYNC_FEASIBILITY.md)。
- `harmony-app/`：继续使用 ArkTS / ArkUI V2；现有 N-API 桥接服务于鸿蒙，不直接复用于 iOS 或 Android。
- `ios-app/`：建议 Swift / SwiftUI，性能敏感区域按需使用 UIKit；尚未建立工程。
- `android-app/`：建议 Kotlin / Jetpack Compose；尚未建立工程。
- iOS / Android 需要另行设计桥接、错误与取消契约、并发及数据生命周期，并验证各自交叉编译工具链；已有 Rust 核心不等于新增平台可以零成本接入。
- 照片库访问、凭据安全存储、系统分享、后台调度等留在平台层；不要让 Rust 核心依赖特定 OS 的 UI 类型。

## 7. 建议实施顺序

1. 定义统一的信息架构、媒体状态、错误状态和高风险操作契约。
2. 以当前鸿蒙客户端验证时间线、查看器和多选流程，沉淀产品语义，而非将鸿蒙外观冻结为三端模板。
3. 为 iOS / Android 各制作最小交互原型，重点验证返回、选图、缩放、分享与权限。
4. 使用相同任务做可用性测试：找旧照片、批量加入相册、区分本地与云端、处理备份失败、理解删除影响。
5. 以任务完成率、误操作、学习成本和浏览性能决定调整，而不是以截图相似度评判。

初期不建议同时铺开三个完整客户端。先建立共用规则，再逐端交付；当前文档和目录不构成对新增技术栈或开发排期的最终决策。
